## 具体原因分析

### 2023年12月 PDF Page 004

缓存内容不是纯粹提取结果，而是包含模型思考式文字，例如“よし、画像は……”和 fenced code block。说明模型在该页没有遵守“只输出页面 Markdown”的要求。

处理方式：删除该页缓存后单页重跑，使用更严格提示词，禁止解释和自我修正。

### 2023年12月 PDF Page 014, 019, 021, 023, 025, 029

这些页均为脚本自动写入的占位页：

`[不确定: Gemini response did not contain text.]`

原因不是 PDF 不清晰；已抽查 Page 014 图像，页面文字清楚。更可能是 Gemini 对这些页面出现空候选、内部过滤、输出异常或短暂服务异常。

处理方式：删除这些页的缓存后单页重跑。若仍失败，改用更高模型或降低页面复杂度。

### 2025年12月 PDF Page 033

页面已输出大量内容，但没有质量注释，且结尾停在 `| <ruby>金<rt` 附近，疑似输出被截断。因此应视为不完整页。

处理方式：删除该页缓存后单页重跑，并提高 `--max-output-tokens`。

## 修复计划

### 第一步：只重跑问题页

不要全量重跑，不要加 `--overwrite` 跑整本。只删除问题页缓存并指定页码重跑。

2023年12月需要重跑：

`4,14,19,21,23,25,29`

2025年12月需要重跑：

`33`

### 第二步：修改提示词约束

单页返工时使用更严格提示：

- 只输出该页 Markdown
- 不要解释识别过程
- 不要输出代码块
- 不要自我修正
- 如果页面内容较多，优先完整提取正文，不要输出 ruby 标签

### 第三步：必要时换模型

如果 `gemini-3.5-flash` 再次空响应，建议对问题页单独改用更强模型，例如账号可用的 Pro 模型。

### 第四步：重建最终 Markdown 和统计

重跑成功后，脚本会自动用缓存重建最终 Markdown。然后再次运行统计脚本：

`F:\N1\tools\summarize_gemini_batch_results.py`
